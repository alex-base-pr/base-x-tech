# Technical SEO / GEO / performance / accessibility audit: v2 build

Date: 2026-09-24 · Build audited: `main` @ `0f57e72`, built as **prod** (`npm ci && npm run build`, no `DEPLOY_ENV`) in a separate worktree. Built with no errors: `sitemap.xml: 26 URLs`, `llms.txt, llms-full.txt (10 pages)`, `qa/check-build.mjs` → `ok`.
Compared against live prod https://base-xtech.com (old site) and https://dev.base-xtech.com (noindex by design, so I did not flag it).

Scope note: QA already covers title ≤60 / description ≤160, title and description uniqueness, one H1, static canonical, robots meta, required JSON-LD `@type`s, llms URL set, sitemap EN set, nav link form, axe critical/serious (without contrast and target-size), and console errors (without third-party errors). This report covers what those tests leave out.

## 1. Release blockers (must fix before prod)

### B1. Cloudflare still returns 403 to GPTBot and meta-externalagent on prod (REQ-041)
Evidence (run today against prod, `curl -A <UA>`):

| UA | `/` | `/llms.txt` |
|---|---|---|
| GPTBot | **403** | **403** |
| meta-externalagent | **403** | **403** |
| Bytespider | 403 (intended) | 403 |
| ClaudeBot, Claude-SearchBot, OAI-SearchBot, PerplexityBot, CCBot, Google-Extended, Googlebot | 200 | 200 |

The new `robots.txt` explicitly invites GPTBot and meta-externalagent (`Content-Signal: … ai-train=yes`), but the edge blocks them. The site says "welcome" and then refuses the request. ChatGPT is the largest AI referrer, so most of the GEO work (llms.txt, JSON-LD, raw-HTML copy) does not reach it.
**Fix:** in Cloudflare → Security → Bots / AI Crawl Control, set GPTBot and Meta-ExternalAgent to Allow (keep Bytespider blocked). Also check the "Block AI bots" managed rule and any WAF custom rule. Then run T-040 against prod with every UA. This is a Cloudflare setting, not code. Change it together with the deploy, not "later".

### B2. The DACH page's FAQ has no FAQPage (REQ-044 is not met)
Evidence: `pages/complex-solutions.html` and `de/pages/complex-solutions.html` each show 8 `<details>` FAQ items ("Questions we get asked" / "Fragen, die wir oft hören"). Their JSON-LD is only `BreadcrumbList, Service, Organization`. The cause: `scripts/seo-plugin.js#faqEntities()` only reads `data-faq-q` / `data-faq-a`, and the complex template doesn't use those attributes. QA misses this because `json/site-map.json` has no `"faq": true` on either complex entry.
**Fix:** add `data-faq-q` / `data-faq-a` to the complex FAQ template (EN and DE), and set `"faq": true` on both site-map entries so T-042 enforces it. This is the page built for the new DACH market, and FAQ is the richest content for AI answers. The fix takes about 10 minutes.

> Not a blocker: **no URL is lost** (see §5). robots.txt, sitemap and llms.txt are correct for prod. There are no JS errors from our own code.

## 2. Should fix (soon after release, or with it if cheap)

### S1. Hreflang clusters are incomplete and contradict each other (existing issue; the new canonicals make it worse)
Evidence (prod build, same on live today):
- EN pages declare `hreflang="uk"` and `x-default` only. There is **no `hreflang="en"` self-reference**, e.g. `/pages/service/shopify-migration-service/` → `uk=…/uk/…`, `x-default=…/pages/service/shopify-migration-service/`.
- UK pages declare `en` and `x-default` = **the UK URL**. So EN says x-default = EN and UK says x-default = UK: the pair disagrees.
- Absorbed pages (theme, headless, app-design, mvp) have `canonical` → the parent page, but their hreflang still pairs themselves with the UK page. Google ignores hreflang on non-canonical URLs, and `/uk/pages/service/mvp-design-services/` points `en=` at a URL that canonicalises somewhere else.
- `ppc-advertising` / `seo-promotion` (EN is noindex; UK is indexable and in the sitemap) use hreflang targets **without a trailing slash**, so every one is a 301 (`hreflang="uk" href=".../uk/pages/service/ppc-advertising"`).
- Only the complex EN/DE pair is correct (`en` + `de` + `x-default`=EN).

**Fix:** in `layout/head-alt.ejs` (lines 14–22), always emit self + counterpart + one agreed x-default (EN) on both sides. For absorbed EN pages, drop the hreflang (or point it at the canonical parent). Add the trailing slash on the ppc/seo alternates. Add a QA check: every hreflang target is 200, self-referenced, reciprocal, and has the same x-default across the cluster. Note: the UK-side fix touches `/uk/` templates. The owner has frozen UK *content*, and this is head markup only, so it needs a one-line owner OK.

### S2. Primary CTA fails WCAG AA contrast (the QA and NFR-002 exemption no longer fits)
Evidence: axe at 375 and 1440 on every EN page. `.v2-pill--accent` "Let's talk" is white on `#81a13f` = **2.95:1**, as are the process icons and the `<strong>` stat numbers. Home also has `.h-step__num` #5a5c63/#040507 = 3.05:1, `.v2-tag--light` #6b6c6d/#e0e0e0 = 3.98:1, and `.v2-help__num` #5d5d5d/#1e2022 = 2.48:1. 13–19 nodes per page. NFR-002 and Q-12 exempt `color-contrast` as "legacy palette, design-owned", but these are **v2 tokens**: the redesign is the design.
**Fix:** use a darker accent for filled buttons (≈ `#5f7a2a` gives ≥4.5:1 with white), or dark text on the green. Raise the number/tag greys to ≥4.5:1. Then remove `color-contrast` from `DESIGN_OWNED` in `qa/tests/a11y.spec.js` for v2 pages.

### S3. No Open Graph or Twitter tags on any page
Evidence: 0 `og:*` / `twitter:*` tags across all 35 built pages (live has none either). LinkedIn, Slack, WhatsApp and Teams previews, which are how B2B buyers pass the link around, fall back to guesses. Some AI and search surfaces also read `og:title` / `og:image`.
**Fix:** in `layout/head-alt.ejs`, emit `og:type=website`, `og:site_name`, `og:title`/`og:description` (reuse title/description), `og:url` (= canonical), `og:locale` (+ `og:locale:alternate`), `og:image` (1200×630, one per service or one shared), and `twitter:card=summary_large_image`.

### S4. Service pages are content dead ends (almost no internal links inside `<main>`)
Evidence: internal (non-blog) links inside `<main>`: 0 on shopify-development, integrations, migration, apps, CRO and complex; 1 on web-design. The only CTA is `href="#"` with `data-form-trigger` (JS only). All authority flows through the header and footer menus, and the topic cluster (migration ↔ integrations ↔ apps ↔ complex) is never linked in the copy.
**Fix:** add 2–4 contextual links per service page, e.g. migration → integrations ("integrations get rebuilt, not carried over"), apps ↔ integrations, development → configurator case, and all of them → complex/DACH where ERP is mentioned. Give the CTA a real fallback `href` (for example `mailto:hello@base-xtech.com` or `#contact`) and keep the JS modal.

### S5. The DE page is not linked in static HTML, and its chrome is English
Evidence: `/de/pages/complex-solutions/` has **0** `<a href>` pointing to it in the built HTML. The switcher links are `href="#"` in the raw HTML and JS fills them in. So only the sitemap and hreflang lead crawlers there. On the DE page itself, the nav, form modal ("Let's talk about your project", "Your name (required)", "Send project details"), footer ("All rights reserved") and the H2 that comes before the H1 are all English. Crawlers and LLMs see mixed-language content.
**Fix:** render the switcher `href`s server-side (the data is already in `json/site-map.json`). Localise at least the modal, CTA and footer strings for `lang=de` (Q-24 is open for this).

### S6. Soft 404: unknown URLs without a trailing slash 301 to `/404/`, which answers 200
Evidence (live today, same `.htaccess` ships in `public/`): `/foo` → 301 `/404/` → **200**. `/foo/` → 404 (correct). The trailing-slash rule also rewrites the internal ErrorDocument request `/404.html` into a 301 to `/404/`. `404.html` has no `noindex` and carries hreflang to `/404/` and `/uk/404/`.
**Fix:** in `public/.htaccess`, add `RewriteCond %{ENV:REDIRECT_STATUS} ^$` to the "/path/file → /path/file/" and ".html → no-ext" rules. Add `<meta name="robots" content="noindex">` to both 404 templates and remove their hreflang.

### S7. Tracking loads before consent on prod (DACH/GDPR risk; existing issue)
Evidence: Lighthouse on live `/` records Clarity and Bing cookies (`c.clarity.ms`, `c.bing.com`) in a fresh profile with no consent given. The `window.allowTracking` gate only checks the hostname and opt-out, not the CookieYes consent state. The new build keeps this head.
**Fix:** start GA, Meta Pixel and Clarity only in the CookieYes `cookieyes_consent_update` callback (analytics/marketing categories), or tag them `type="text/plain" data-cookieyes="cookieyes-analytics"`. Legal risk rather than SEO, but the DACH page makes it relevant now.

### S8. llms-full.txt is padded with UI boilerplate
Evidence: 53.9 KB. Every page section starts with the form modal ("Let's talk about your project / Thank you — your project details are with us / Sorry, the form didn't send", 10× each). Other repeats: testimonials twice (slider clones), counter junk ("… 0 - 1", "0 - 2"), "[ Scroll to Explore ]" 6×, "When We Can Help", "FAQ", "Client Stories" 6×. `llms.txt` gives the Home line as its `<title>` and not a summary, and it has no contact email: the email only appears in the modal error strings, and on the page Cloudflare Email Obfuscation turns `mailto:` into `/cdn-cgi/l/email-protection#…` (live and dev).
**Fix:** in `scripts/postbuild.mjs#pageText()`, strip `[data-form-modal]`/`dialog`, `[aria-hidden="true"]`, slider clones and `.v2-help__num`-style counters. Dedupe identical lines per page. In `llms.txt`, add a "Contact: hello@base-xtech.com" line and the home meta description. Optionally turn off Cloudflare Email Obfuscation (or add `email` to Organization JSON-LD) so crawlers can read the address.

### S9. Organization entity is thin
Evidence: `Organization` = name, url, logo (the favicon PNG), and sameAs LinkedIn/Behance/Upwork. The Clutch profile is linked on Home but missing from sameAs. GoodFirms and Sortlist badges are embedded but not listed either. There is no `email` / `contactPoint`. `WebSite` has no `inLanguage`, and the DE `Service` has no `inLanguage`/`areaServed` although the copy says DACH.
**Fix:** add `sameAs` Clutch (+ GoodFirms and Sortlist profile URLs if they exist), `email: hello@base-xtech.com`, `contactPoint {contactType: "sales", email}`, `areaServed` for DE/AT/CH on the complex Service, and a proper logo file (SVG/PNG wordmark, not the favicon). Only facts already on the site, per REQ-044.

### S10. Render-blocking head: CookieYes (sync) + two full CSS bundles
Evidence: Lighthouse on the prod build served locally (CookieYes present, unlike dev). The render-blocking chain is `cdn-cookieyes.com/…/script.js` ~1000 ms, `v2-*.css` (68 KB raw) and `main-*.css` (90 KB raw, mostly the legacy design). v2 pages load both bundles. The result was FCP 3.2–3.5 s and LCP 4.0–4.2 s with no compression. On dev (no CookieYes, brotli), FCP was 1.9–2.6 s.
**Fix:** load CookieYes `async` (it supports it), or at least `<link rel="preconnect" href="https://cdn-cookieyes.com">`. Split legacy `main.scss` so v2 pages ship only v2 + shared CSS (Lighthouse: 14 KB unused CSS, 34 KB unused JS). Load the Sortlist badge script only on the page that has `.sortlist-badge` (home). It is requested on every page, and from non-prod origins the request fails with `ERR_BLOCKED_BY_RESPONSE.NotSameOrigin`.

## 5. Lost-URL check: **pass, no URL disappears**

Method: every `<loc>` in https://base-xtech.com/sitemap.xml (30 URLs, no-slash form), plus every internal link on live `/`, `/uk/`, `/pages/shopify-development/` and `/uk/pages/shopify-development/`: 31 unique paths. Each was mapped to a file in the new `dist/` and requested in slash form from a static server that mimics the prod `.htaccess`. **31/31 return 200.**

- EN: all 15 old URLs are still served. 9 are indexable. 4 are absorbed with `canonical` → parent (theme, headless → shopify-development; app-design → apps; mvp → web design). 2 are `noindex, follow` (ppc, seo). There are no redirects, as the owner decided.
- UK: all 15 are unchanged and in the new sitemap.
- New: `/pages/complex-solutions/`, `/de/pages/complex-solutions/` (live currently 301s them to `/404/`). The generic `.htaccess` rewrite (`%{DOCUMENT_ROOT}/$1.html -f`) will serve them after deploy.
- `/blog/**` is not in `dist/` and is served separately. All 7 `/blog/…` URLs linked from the build return 200 on live. Both sitemaps in robots.txt resolve (200).
- Sitemap change: the new sitemap uses the canonical trailing-slash form (the old one listed URLs that 301). The 6 absorbed/noindex EN URLs are removed from it. Both are intended (REQ-008/009).
- Deploy caveat: `rsync --delete ./dist/` over the live path is unchanged from today, so whatever serves `/blog/` today is unaffected. Confirm once that `/blog` is not inside `REMOTE_LIVE_PATH`.

## 6. What is already good (checked, no action)

- Prod build: no `noindex`, no `X-Robots-Tag`, `robots.txt` = REQ-040 (named AI bots allowed, `Disallow: /analytics-optout/`, Bytespider blocked, both sitemaps).
- Canonicals are static, absolute and in trailing-slash form on every page. - Copy is in raw HTML inside `<main>`. llms.txt lists exactly the 10 indexable pages with meta descriptions.
- Images: all `<img>` have `alt` (decorative ones use `alt=""`). Everything is WebP except 3 PNG logos on home. Below-the-fold images use `loading="lazy"`, and the hero has `fetchpriority="high"`. Measured CLS is ≤ 0.05 even though mobile-nav thumbnails have no width/height.

- Prod caching on live: hashed assets have `max-age=31536000` and are served with brotli.
